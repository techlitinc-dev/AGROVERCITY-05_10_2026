# Conventions 01 — LLM Coding Rules

The code for this project is generated by a less-capable LLM driven task-by-task by a human operator. These rules are **mandatory** and apply to every prompt, every file, every commit. If a rule conflicts with an impulse to be clever, the rule wins.

## 1. Task Execution Rules

1. **One task per prompt.** A task is one numbered subtask in a `docs/days/day-NN.md` file. Never implement two tasks in one prompt. Never "also fix" unrelated code.
2. **Always include context in the prompt.** Each prompt must paste: (a) the task text from the day file, (b) this file, (c) `conventions/02-api-conventions.md` if the task touches the API or API client, (d) the relevant section of `docs/schema/firestore-collections.md` or `docs/schema/redis-keys.md` if the task touches data.
3. **Never invent endpoints, fields, or collection names.** Sources of truth, in order:
   1. `endpoints.json` + `endpoints.md` (repo root) — base API.
   2. `docs/overview/03-gap-analysis-new-screens-and-endpoints.md` — new endpoints/screens.
   3. `docs/schema/firestore-collections.md` and `docs/schema/redis-keys.md` — data shapes.
   If something you need is defined nowhere: **stop**, report the gap to the operator, and add it to the gap-analysis doc before writing code.
4. **Max ~300 lines per file.** If a file would exceed 300 lines, split it (e.g. `mandi_screen.dart` → `mandi_screen.dart` + `mandi_widgets.dart`; a large router → two routers under the same prefix). State the split in your reply.
5. **After every task, run its Test command.** Every day-file task ends with `Test: <command>`. Run it verbatim from the repo root (or the stated working directory), paste the full output into your reply, and state PASS/FAIL.
6. **If the test fails, fix before moving on.** Never skip a failing test, never delete or weaken an assertion, never comment out code to make it pass. Iterate until green, or report the blocker explicitly.
7. **Do not add packages/dependencies not listed in the day file.** The day file lists the exact packages (`pubspec.yaml` / `requirements.txt` lines). If you believe a missing package is required, stop and ask the operator — do not improvise.
8. **Do not edit `flutter-prototype/`.** It is read-only reference material.

## 2. Backend Rules (Dev A)

1. **Pydantic v2 models for every request and response body.** Define them in `backend/app/models/<domain>.py` before writing the router. No `dict` responses, no untyped bodies.
2. **Routers are thin.** A router function only: declares path/method, applies deps (`get_current_user`, `require_roles(...)`, idempotency), calls one service function, returns the Pydantic model. All logic lives in `backend/app/services/`.
3. **All I/O is async.** Async Firestore/Redis clients, `httpx.AsyncClient` for external calls. No blocking calls in handlers.
4. **Money is integer rupees** everywhere in the API and Firestore (see `conventions/02-api-conventions.md` §8). Dates are ISO-8601 strings. Never floats for money.
5. **Every list endpoint uses the pagination envelope** `{ data, page, pageSize, total }`. Every error uses the error envelope. No ad-hoc shapes.
6. **Writes accept `Idempotency-Key`** and are safe to replay (see `core/idempotency.py`).
7. **Never log PII or secrets:** no Aadhaar numbers, MPINs, OTPs, tokens, or API keys in logs. Log `uid`, route, status, latency.
8. **Tests:** every router gets a `tests/test_<router>.py` with at least the happy path and the ACL check (wrong role → 403). Use the fixtures in `tests/conftest.py`.

## 3. Flutter Rules (Dev B)

1. **Reuse prototype widgets first.** Before writing any widget, check `flutter-prototype/lib/` for an existing implementation and **port it** (copy → adapt imports → wire to real API data). The visual language (glass cards, staggered fades, Mukta font, persona colors) must match the prototype.
2. **Screens never call Dio directly.** All HTTP goes through an `apps/mobile/lib/api/<domain>_api.dart` class. All paths come from `apps/mobile/lib/api/endpoints.dart` constants — string literals for paths are forbidden in screens and API classes.
3. **Field names match the API exactly.** Dart model `fromJson`/`toJson` use the same camelCase keys as the API payloads. No renaming, no extra client-only fields in shared models.
4. **State stays in `AppState`** (`state/app_state.dart`, ChangeNotifier) with the prototype's `currentRoute` + `AnimatedSwitcher` router. Do not introduce Navigator routes, go_router, or a new state library.
5. **Vernacular-first UI.** Labels come from `core/i18n.dart` string tables; never hard-code user-visible Hindi/Marathi strings in a screen.
6. **Accessibility floors:** 48×48dp minimum tap targets, WCAG AA contrast against the light palette, respect reduced-motion.
7. **Tests:** each new screen gets a widget test that renders it with a fake API client and pumps the happy path.

## 4. Comment & Documentation Style

1. **Default: no comments.** Code should be self-explanatory. Do not add comments that restate what the code does.
2. **Allowed comments:** (a) non-obvious business rules (e.g. `// max 2 slots/farmer/day — server-enforced, 409 on third`), (b) external-API quirks, (c) `TODO(day-N)` markers for work explicitly scheduled later.
3. **No docstrings on every function.** Add one only where the contract is non-obvious (e.g. idempotency middleware).
4. **No "changed by / date / author" headers.** Git tracks that.
5. **No README/docs files unless a task asks for one.**

## 5. Definition of Done (per task)

A task is done only when ALL are true:

1. Code compiles / analyzes clean (`flutter analyze` / `ruff check` + `mypy` as configured on Day 1).
2. The task's `Test:` command passes and its output is pasted in the reply.
3. No files outside the task's stated scope were modified.
4. No endpoint, field, package, or route was invented.
5. Files are under the 300-line limit or the split is reported.

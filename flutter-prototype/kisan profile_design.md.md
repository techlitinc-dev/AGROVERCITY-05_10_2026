[File Change Matrix](#7-file-change-matrix)8. [Future Considerations](#8-future-considerations)---## 1. Executive SummaryKisan Setu currently serves a single user persona — the **Farmer (किसान)**. While the app ships 18 module views covering mandi prices, equipment rental, transport, and more, every user sees the same interface regardless of their actual role in the agricultural supply chain.This document describes the design for a **Multi-Profile System** that introduces six distinct user personas into Kisan Setu: Farmer, Farm Landlord, Transporter, Seller/Vyapari, Equipment Rental Owner, and Broker/Dalal. Each persona gets a curated home dashboard, filtered navigation, and role-specific tools — while a single user account can link multiple profiles and switch between them seamlessly.The design preserves the existing `AppState` + `ChangeNotifier` architecture with zero breaking changes to the 18 existing views. The Farmer profile retains full access to all routes; other profiles see a permission-filtered subset.---## 2. Persistence Strategy**Package:** `shared_preferences: ^2.2.3`**What is persisted:**| Key | Type | Default | Description |`----`|------|---------|-------------|`activeProfile` | `int` (enum index) | `0` (farmer) | Index into `UserProfileType.values` |`isOnboarded` | `bool` | `false` | Whether onboarding is complete |`language` | `String` | `'hi'` | Selected UI language |**When persistence happens:**- After `selectProfileDuringRegistration()` — first-time profile selection- After `switchProfile()` — profile switch- After `completeRegistration()` — onboarding completion- After `selectLanguageAndProceed()` — language change**When persistence is read:**- `loadPersistedState()` is called in `main()` before `runApp()`**Startup Sequence:**```dartvoid main() async {  WidgetsFlutterBinding.ensureInitialized();  final appState = AppState();  await appState.loadPersistedState();  runApp(KisanSetuApp(appState: appState));}```**Why SharedPreferences and not a database:**- Profile state is 3 scalar values — no relational data- Zero migration burden- Synchronous-read API via cached instance- Sufficient for the current scope; can be upgraded to Hive/SQLite if profile-specific settings grow**Note:** `linkedProfiles` is NOT persisted in Phase 1. It defaults to `[farmer]` on every app launch. Multi-profile linking persistence will be added in Phase 2 when user accounts are backed by a backend service.---## 5. Design Decisions & Trade-offs### Decision 1: Enum-Based Profiles vs. String-Based**Chosen:** Enum-based (`UserProfileType`)**Alternative considered:** String identifiers (`'farmer'`, `'transporter'`, etc.)**Rationale:** Enums provide compile-time exhaustiveness checking. Adding a new profile forces the developer to update the registry and route map — no orphaned string literals. Dart's switch expression exhaustiveness is a significant safety net.**Trade-off:** Adding a new profile requires a code change (new enum value) rather than a data/configuration change. This is acceptable because profiles are tightly coupled to app behavior (routes, home views, colors) and should go through code review.### Decision 2: Central Registry vs. Distributed Metadata**Chosen:** `UserProfileRegistry` as single source of truth**Alternative considered:** Metadata embedded in each view/widget**Rationale:** A farmer's icon, color, and label appear in at least 4 places (onboarding card, top bar badge, tools sheet, home header). Distributing this data would create synchronization bugs. The registry pattern ensures consistency with zero effort.**Trade-off:** Slight indirection — views must call `UserProfileRegistry.meta(type)` instead of using literals. This is mitigated by the `activeProfileMeta` getter on AppState.### Decision 3: Navigation Guard in `navigateTo()` vs. Route-Level Middleware**Chosen:** Override `navigateTo()` in AppState**Alternative considered:** Wrapper widgets that check permissions before rendering**Rationale:** Kisan Setu uses a string-based routing system (not Flutter's Navigator 2.0 or GoRouter). All navigation flows through `AppState.navigateTo()`. Guarding at this single point provides complete coverage with minimal code. No route-level wrapper is needed.**Trade-off:** If direct `Navigator.push()` calls exist outside of `AppState.navigateTo()`, they would bypass the guard. The codebase audit confirms all navigation goes through AppState.### Decision 4: Farmer as Super-User vs. Equal Profiles**Chosen:** Farmer sees all 18 routes; others see curated subsets**Alternative considered:** All profiles see only their specific routes**Rationale:** In rural India, a farmer frequently performs multiple roles — they grow crops, transport them to market, and sell directly. Restricting the farmer profile would degrade the existing user experience. The Farmer persona preserves 100% backward compatibility.### Decision 5: Multi-Profile Linking vs. Single Profile Per Account**Chosen:** One account can link multiple profiles**Alternative considered:** Separate accounts per persona**Rationale:** A single farmer might also run a transport side-business and broker deals. Forcing account switching (phone OTP each time) would be hostile UX. Multi-profile linking with instant switching via dropdown is significantly smoother.### Decision 6: SharedPreferences vs. No Persistence (Phase 1)**Chosen:** Persist active profile, onboarding state, and language**Alternative considered:** No persistence — always start as farmer**Rationale:** Without persistence, a transporter would have to re-select their profile every time they open the app. This would make the feature unusable in practice. SharedPreferences adds minimal complexity.---## 6. Backward Compatibility### Zero Breaking ChangesThe following are guaranteed unchanged:1. **All 18 existing views** — no file modifications, no import changes2. **Existing `HomeView`** — wrapped by `FarmerHomeView`, behavior identical3. **`AppState` existing API** — all existing methods and fields preserved4. **`ListenableBuilder` pattern** — no Provider/Riverpod migration needed5. **Onboarding flow** — new profile step is inserted between language and registration, existing steps unchanged6. **Default behavior** — new users default to `UserProfileType.farmer`, existing users (no persisted state) also default to farmer### Migration Path for Existing Users- Users who have already completed onboarding will have `isOnboarded: true` in SharedPreferences but no `activeProfile` key- `loadPersistedState()` defaults to `UserProfileType.farmer` (index 0) when key is missing- These users see the exact same app they've always seen — no surprise, no re-onboarding---## 7.

## 1. Ground truth — what the backend implements today

### 1.1 The broker chain as shipped

The backend implements a **broker-side deal desk**, not a full two-sided marketplace yet:

1. A broker (JWT + `activeProfile == "broker"`, enforced by `require_role` → 403 `FORBIDDEN_ROLE`) records a **deal** between a buyer and a seller (`POST /broker/deals`). Buyer/seller are plain name/phone strings — they have no accounts on the other side.
2. The broker negotiates via **structured messages** on the deal (`GET/POST /broker/deals/{id}/messages`). A message carries `senderRole: broker|buyer|seller`, `text`, and an optional `amountOffer` (₹/quintal) — this is the spec's C6 "structured negotiation card" hook.
3. The broker drives the deal through its lifecycle with `PUT /broker/deals/{id}` (`status`, rate, quantity, terms).
4. Server auto-computes `grossAmount = quantityQuintals × agreedRate` and `commissionAmount = gross × brokerCommissionPct / 100` (default pct 2.0, allowed 0–10) on create and on rate/qty update.
5. **Leads** (`GET/POST /broker/leads`, `PUT/DELETE /broker/leads/{id}`) are a lightweight CRM for farmer/buyer/trader contacts.
6. `GET /broker/commissions` aggregates: `totalEarned` (Σ commission where status `completed`), `pendingPayout` (Σ where status ∈ negotiating/contract_issued/accepted/in_transit), plus deal counts.
7. `GET /broker/settlements` returns weekly settlement docs (`pending → approved → paid`), generated by cron `POST /jobs/settlements/run`.

⚠️ **Fallback quirk:** `GET /broker/deals` returns other brokers' demo deals (`omni-user-777`, `dev-user-1`) when the caller has none. The website must filter client-side to `deal.brokerId === session uid` so a new broker never sees someone else's deals.

### 1.4 Known backend gaps that shape this plan

- **No farmer-side counterpart.** A farmer cannot see, accept, or counter a deal. Buyer/seller are unauthenticated strings. Farmer flows in §5.2 are gated on prerequisite **P2** (§3).
- **No ownership checks.** Any broker can `GET/PUT/DELETE` any deal by id (403 `FORBIDDEN_ROLE` only checks the role). Prerequisite **P3**.
- **Settlement bug.** `services/settlements.py` reads `deal.valueRupees or deal.dealValueRupees`; the deal schema stores `grossAmount` — broker settlements generate with `grossRupees: 0`. Prerequisite **P1** (must land before the commissions page is meaningful).
- **No evidence upload for deals.** No deal-scoped photo endpoint (spec F8/B10: harvest/loading/weighbridge photos). PhotoUploader exists in the trade module; wiring needs an upload target → optional **P4**.
- **Deal messages are unmoderated free text.** Spec D4 (phone-number regex, URL blocklist) is not enforced server-side. The web UI must run the D4 ingress filter client-side pre-send and keep pre-booking comms structured (§9).
- **No realtime.** Negotiation and chat are REST polling; spec's Socket.IO was never built. v1: poll on focus / pull-to-refresh / `setInterval` while a deal detail is open.
- **`endpoints.md:44` documents `GET /users/me/dashboard/{profileType}` — not implemented.** brokerHome must be composed client-side from `/broker/deals`, `/broker/leads`, `/broker/commissions`, `/broker/settlements`, `/mandi/*` (this matches what the mobile app's `BrokerHomeView` does with local/demo state).

## 2. Design principles (ease-of-use contract)

Both personas are low-digital-literacy users; brokers are time-poor (mandi hours), farmers are phone-first.

**Shared**
1. **Visible math, no hidden commission.** Every deal screen shows the three-number card: `Gross = Qty × Rate`, `Commission (−)`, `Farmer payout (=)`. Same card for broker (earnings view) and farmer (payout view). Never make a user calculate.
2. **Benchmark everything.** Every rate input/offer card sits next to the mandi modal price (`GET /mandi/compare` via the existing `PriceWithBenchmark` component), with delta shown as "₹X above/below mandi".
3. **Plain-language statuses.** StatusPill captions are sentences, not state names: `negotiating` → "Price बातचीत चल रही है", `contract_issued` → "Contract ready — accept करें", `in_transit` → "गाड़ी रास्ते में".
4. **No typing where a picker works.** Crop/grade/mandi pickers from existing master lists (mandi crops, `marketsServed`), quantity via `QuantityStepper`, rate via stepper seeded from mandi benchmark.
5. **Mask all phone numbers** (spec C1): display `+91 •• •••• •006` everywhere; numbers are never shown, copied, or linked (`tel:`).
6. **Offline tolerance (C12).** Deal/lead forms autosave drafts to localStorage; submit button shows "saved — will send when online" when `navigator.onLine === false`.
7. **Hindi + English parity.** Every string in `en.broker` + `hi.broker` from day one; default follows the existing language store.

**Broker-specific**
8. **Speed: 3 taps from home to a recorded offer.** brokerHome → "New Deal" → prefilled form (last-used buyer, today's mandi rate for chosen crop) → save.
9. **Pipeline view first.** Deals list opens as status-grouped sections (Kanban-lite) so the broker sees what needs action today (pickups, counters waiting, contracts to issue).
10. **Lead → Deal in one tap.** A lead card has "Make deal" that pre-fills the deal form (party name/phone, commodity, target rate) and marks the lead `converted` on success.
11. **Commission preview while negotiating.** The negotiation thread shows running commission for any `amountOffer` before the broker sends it.

**Farmer-specific**
12. **Offer = one card, one decision.** Farmer opens brokerOffers → sees the offer card (who, what, qty, rate vs mandi, payout math) → `Accept / Counter / Decline` — no forms, no jargon.
13. **Counter without typing.** Counter = stepper (−/+) around the current offer with suggested steps (e.g. ₹25/q), plus a "suggest fair price" chip from mandi modal.
14. **Trust before booking.** Broker identity = name, mandi/markets served, years (from profile), completion count — no phone, no external links.
15. **Chat is a door that opens, not a form to find.** Post-acceptance the chat button simply appears on the deal card with a "chat unlocked" celebration state (spec D1).

## 8. Error & edge-case handling (UI contract)

| Case | UI behavior |
|---|---|
| 403 `FORBIDDEN_ROLE` | `useEnsureProfile` activation sheet (existing pattern) — offer "Activate broker profile" one-tap |
| 404 `DEAL_NOT_FOUND` / `LEAD_NOT_FOUND` | EmptyState "This deal no longer exists" + back to list; farmer 404s stay 404-shaped (never leak existence — P2 contract) |
| Validation (`quantityQuintals>0`, `agreedRate>0`, pct 0–10) | Inline field errors from `ApiError.fieldErrors`; `DealMathCard` greys out until valid |
| Cancel after `accepted` (spec E1/E2) | `ConfirmSheet` with mandatory reason; farmer cancel ≤30 min free (UI note), later = warning about fee; broker cancel = strike warning copy |
| No-show (E3/E4) | v1: "Report no-show" on Timeline → posts a flagged message + notification to admin (dispute-lite until C9 exists) |
| Unresponsive party (E12) | Deal detail shows "No reply for Xh" banner + one-tap reminder card |
| Offline (C12) | Draft saved chip; submit disabled → "will send when online"; queue one retry on `online` event |
| Demo-deals fallback | Filtered to own `brokerId` (§1.1); developer flag to view samples |
| Phone in any text field | `D4TextGuard` blocks send, shows warning toast with the matched rule (no content leaves the client) |
| Weight/quantity mismatch at delivery (E6) | `completed` confirm sheet asks "weighed quantity" — if ≠ booked qty, show pro-rata adjusted math card (adjusted payout = weighed × rate) and write it into notes; full auto-adjustment waits for backend support |
